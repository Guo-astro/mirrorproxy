## 原始发现：major（均已修复）

1. **加载与失败状态不完整（交互状态检查）** — `web/src/pages/admin-email.tsx:23–34,80`；同类模式见 `admin-providers.tsx:24`、`admin-sessions.tsx:20`。
   邮件设置在 SMTP 请求失败时可能完全留白；邀请列表请求失败则保留初始空数组，容易被理解成“没有邀请”。没有明确加载状态和重试入口，用户无法区分等待、失败与无数据。
   → 分离各区块的 loading / error / empty / success，使用 Skeleton、带重试操作的 Alert，并保留已成功加载的区块。
   证据为代码路径和本地故障注入：SMTP API 返回 503 时，浏览器检测到设置卡片、错误 Alert 和重试按钮均为 0；未注入生产故障。

2. **操作中的状态和失败反馈不完整（交互状态检查）** — `web/src/pages/admin-email.tsx:61–68`。
   邀请撤销未检查 DELETE 的响应状态；重新发送与撤销未设置按记录禁用或处理中状态。弱网络下可能连续点击，失败后缺少一致反馈。
   → 为每条记录维护 busy 状态，检查 HTTP 状态并捕获网络失败，通过现有 OperationToast 提示；完成后再刷新。保留撤销确认及现有 CSRF 边界。
   这是前端反馈缺口，不表示后端会绕过权限或重复提交保护。

3. **装饰性眉题（Eyebrow on every section）与本地化缺口** — `web/src/pages/portal.tsx:177,280`。
   `MIRRORPROXY / ACCELERATION DESK`、`OCI DISTRIBUTION` 位于已有标题上方，没有步骤或章节作用；`REGISTRIES` 数量说明也固定为英文。中文模式仍出现这些英文装饰，给任务型首页增加阅读层级。
   → 删除重复的装饰眉题；保留有用的镜像仓库数量，并接入现有双语文案。不要改变现有转换器、目录和安装区的结构。

4. **窄屏表格密度（响应式可读性检查）** — `web/src/pages/admin-health.tsx:26–33`。
   五列表格使用固定布局，源名称占 42%，其余四列分配剩余宽度。320 像素下容器仅约 240 像素，列标题、适配器和检测时间接近逐字竖排；40 条记录形成过长的页面。无横向溢出断言通过，并不等于可读性通过。
   → 小屏使用表格内横向滚动并保留合理最小列宽，或将“适配器、耗时、检测时间”合并为摘要行；保留源名称、检测结果和展开上游的能力。不要通过缩小字号或隐藏内容处理。
   证据：本地 Chromium 的 `health-table-light-320.png` / `health-table-dark-320.png` 截图；首次审计时只修复圆角；后续修复已增加表格内横向滚动，见下方修复记录。
